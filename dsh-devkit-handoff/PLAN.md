# 实施计划

## 1. 目标与默认决策

项目暂名 **DSH DevKit**，是本项目名称，不是 DSH 官方产品或既有 npm 包。

目标是积累可复用的研发插件：工作区、上下文、执行器、验证、审核、任务与报告；业务流程按 Bug 修复、UI 修复、需求开发逐步增加。

新项目默认 TypeScript strict + ESM，优先使用与选定 DSH 版本兼容的 Node 与包管理器。已有插件项目沿用其工具链，不为了形式统一而重构。第一版可以只有一个可安装组合包、多个独立导出的插件模块，不强制拆成多个仓库或微服务。

**实施顺序：M0 → M1 → M2 → M3。M4/M5 是后续迭代，不属于首轮默认执行范围。**

## 2. M0：环境、代码与 API 核验

### 要做的事

- 读取当前仓库及上层适用的 `AGENTS.md`、README、package manifest、lockfile、已有 DSH 配置和插件实现。
- 区分“插件源码仓库”与“插件未来要操作的业务仓库”。不得默认两者相同。
- 核对当前安装的 DSH、Cordis、Node、Codex 及相关适配器版本。存在可用版本时优先沿用；新项目选择一个实测兼容版本，并锁定，而非写 `latest`。
- 按 `SOURCES.md` 对照实际类型、源码和安装帮助，核实插件导出、bundle/profile、工具注册、子代理启动、取消、模型路由、沙箱及权限机制。
- 记录 Codex 与审核路由是否可用，只记录凭据引用/可用状态，不读取并展示明文密钥。
- 只做与实施有关的最小架构扫描，不把全仓库调研变成无期限前置项目。

### 必须产出

`docs/ENVIRONMENT.md`、`docs/DSH_COMPATIBILITY.md`、`docs/IMPLEMENTATION_STATUS.md`、必要的 `docs/adr/0001-layout-and-runtime.md`。

兼容性报告应含每个使用接口的包、符号、版本、类型或源码路径、核验结果，以及调用能力是否实际支持。

### 通过条件

已经知道真实接入路径，能解释代码应写在哪里、如何挂载、如何验证；不凭记忆编造 DSH API。若缺少外部访问但本地依赖足够，继续本地核验；本地和外部证据均不足时，只阻塞相应适配器，继续可独立完成的领域逻辑和测试。

## 3. M1：真实 DSH 插件骨架

### 要做的事

- 建立一个组合包及多个可独立装配的插件入口；不用修改 DSH agent loop。
- 实现 `devkit_doctor`，报告配置、服务依赖、版本、路由和安全能力。
- 实现任务创建、查询的最小真实工具，参数和输出具备运行时校验。
- 提供针对独立测试 profile / 独立 Harness home 的安装和启动步骤。
- 提供卸载/停止资源的生命周期处理及重复挂载测试。
- 确认模型可见工具输出与程序读取的规范结果一致；不得从一句自然语言中猜任务 ID。

### 必须产出

可构建的插件包、真实 DSH 装配配置、原生注册与分派测试、安装/移除说明。

### 通过条件

在真实 DSH runtime 上，`devkit_doctor`、创建任务、查询任务可以调用并返回校验后的结果。只在自行模拟的 Context 上调用 `apply()` 不足以通过此里程碑。

## 4. M2：公共能力与确定性控制

### 要做的事

- 完成任务合同、状态机、策略快照、证据快照和结果协议。
- 实现任务持久化、同任务防重、任务拥有权与单写入执行控制。
- 实现工作区提供方：独立任务工作目录、精确基准版本、脏目录保护、安全的产物采集。
- 实现验证运行器：可信命令计划、超时、取消、退出码、日志、执行前后快照检查。
- 实现报告与待办问题导出；不依赖外部 GitHub/工单写入。
- 完成权限边界、不可自我批准、保护测试和配置、网络与文件权限能力检查。

### 必须产出

公共插件模块、持久化迁移/版本策略、单元与集成测试、安全和恢复说明。

### 通过条件

即便不调用模型，也可以通过测试证明：错误证据不能使状态跳到成功，越权被阻止，重复运行不会产生两个写入者，取消/重启不会无条件重放任务。

## 5. M3：可复现 Bug 修复闭环（v0.1）

### 要做的事

- 接收结构化任务与原始自然语言描述，生成并校验任务合同。
- 复现失败并冻结验收证据；区分断言失败与依赖缺失、命令不存在等环境错误。
- 通过实际 DSH Codex 子代理提供方接入主要代码执行器；不重复实现已有协议。
- 接入一个真实独立审核适配器，优先使用已配置的 DeepSeek 模型路由。未配置时正确阻塞真实运行。
- 执行 `复现 → 修改 → 快照 → 验证 → 独立审核 → 分诊 → 有限返修 → 本地报告`。
- 实现确认 P0/P1 阻塞、P2/P3 待办、证据不足人工处理、验收失败始终阻塞的规则。
- 建立明确的 `native-fixture` 与 `live` 验证模式，禁止混淆。

### 必须产出

一个故意带 Bug 的临时样例仓库生成器、成功及失败场景、真实执行器/审核适配器实现、测试报告、Quickstart、配置样例、已知限制。

### 通过条件

满足 `ACCEPTANCE.md` 中 v0.1 项目。无凭据时允许交付完整适配器代码与离线/原生测试，但必须标记“真实模型验证阻塞”，不能将 M3 的 live 验证勾为通过。

**本期结束状态：生成待人工验收的本地产物。不是自动合并，更不是自动上线。**

## 6. M4：UI 修复（v0.2）

复用 M2/M3，不复制任务服务、执行器、审核和报告。

新增页面/路由与启动方法、截图参照或明确视觉目标、视口与浏览器配置、Playwright 浏览器验证、前后截图及可视差异、交互/控制台错误检查。

截图不等于验收。视觉模型不可用时不得宣称视觉评审完成；没有设计参照的“更好看”进入目标确认，而非擅自重设计。

通过条件：一个确定的 UI 缺陷在固定环境下可复现、修复并验证；无需新增另一套任务系统。地图/Canvas/3D 场景必须有对应行为验证，不能只比较 DOM。

## 7. M5：需求开发（v0.3）

新增需求合同、业务规则与假设清单、方案、验收映射、必要审批。

已有代码或文档能回答的问题由 Agent 自查；无法确认且会影响权限、接口契约、数据模型或业务行为的决策进入人工确认。确认后冻结验收与范围，再开发。

通过条件：一个范围明确的小功能能够复用公共执行、验证和审核链路，并形成“需求条目 → 实现 → 测试/证据”的映射。

## 8. 首版不做

插件市场、通用可视化流程编辑器、Dify、MCP 网关、Kubernetes、多租户、多仓库并发修改、自动 push/合并/发布、生产数据库访问、自动给全部审核模型开通账号、机器人运行时控制。

此处“不做”指首版范围，不代表永久排除。Claude Code/GLM 的扩展接口可保留，但不得写空壳后将它们标记为已支持。

## 9. 交付与继续方式

每个里程碑完成后更新状态文档和真实验证证据。遇到一个适配器阻塞，不应让其它独立工作停摆。

单次上下文不能完成全部工作时，留下已实现文件、已运行测试、阻塞点和下一条明确任务；不把未完成项勾为完成。下一次使用 `CODEX_CONTINUE.md` 的“继续当前阶段”提示词。

不提供基于猜测的工期和成功率；首先以完成定义和测试证据管理交付。
