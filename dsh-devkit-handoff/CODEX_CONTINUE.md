# 后续执行提示词

每次只使用对应阶段的一段。不要把三期任务同时粘贴成一次全量重写。

## A. 继续当前首版

> 继续 DSH DevKit 的 M0–M3。先读适用 AGENTS.md、dsh-devkit-handoff/ 下的 PLAN、SPEC、ACCEPTANCE，以及 docs/IMPLEMENTATION_STATUS.md、docs/TEST_REPORT.md 和当前 git diff。根据实际文件与测试恢复进度，不只依赖上一条总结。优先完成尚未通过的最高优先级里程碑，保留用户未提交修改，不重新初始化、不重复造接口。缺外部配置只阻塞相关 live 验证，继续完成其它实现。不要进入 M4/M5，不改弱验收规则，不把未验证标通过。完成后更新状态与真实验证证据。

## B. 根据独立审计修复

> 读取最新独立审计结果并逐条核对代码。优先修复确认成立的 P0/P1，补充能复现问题的测试，再修改实现并重跑相关及回归测试。证据不足的高风险问题先补证，不直接忽略；非阻塞 P2/P3 去重写入本地待办。不要通过弱化 SPEC、删除测试、跳过审核或提高权限解决问题。保留每条 finding 与修复证据的对应，最后重新进行独立审计。全程不 push/merge/deploy。

## C. 实施 UI 修复插件（v0.2 / M4）

> 现在实现 DSH DevKit 的 M4，先读取 dsh-devkit-handoff/SPEC.md 第 13 节及现有代码与测试。复用现有任务、持久化、工作区、执行器、审核和报告，不复制另一套流程基础设施。实现 ui-fix 任务合同、页面启动计划、固定视口/浏览器、参照材料、Playwright 验证、修复前后截图、视觉差异及交互检查。视觉模型必须实际支持图片且完成传递验证，不可用时明确阻塞视觉验收。执行器不能随意重写基准图或阈值。创建临时前端 fixture 验证一个确定的遮挡/溢出问题，不动真实业务仓库。原 v0.1 回归测试必须保留并通过，新增验收与使用文档。不要同时开始需求开发插件，不自动 push/merge/deploy。

## D. 实施需求开发插件（v0.3 / M5）

> 现在实现 DSH DevKit 的 M5，先读取 dsh-devkit-handoff/SPEC.md 第 14 节与已有公共能力。新增 feature 任务合同、需求与假设整理、验收映射、方案和高影响审批。已有代码/文档能回答的问题自行查证；无法确认的业务规则、权限、数据迁移和公共接口变更进入受信任人工确认，不擅自补全。合同冻结后复用现有工作区、Codex 执行、验证、独立审核及报告。使用临时 fixture 演示一个明确的小功能，并证明每条验收有对应证据。保留 v0.1/v0.2 回归，不引入独立调度平台、不自动 push/merge/deploy。
