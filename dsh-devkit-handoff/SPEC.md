# DSH DevKit · 产品与技术 Spec

Spec 版本：1.0 · 2026-09-20  
默认实施范围：M0–M3 / v0.1。M4/M5 只定义扩展合同，不要求首轮实现。

**下文的项目名、模块名、工具名、配置及数据协议均为本项目拟实现的设计，不是 DSH 官方现成接口。** 使用 DSH 的真实接口必须按 `SOURCES.md` 和锁定版本核验。

## 1. 产品定位与成功标准

为个人或小团队提供可组合的研发辅助插件：用户给出一个任务，系统整理上下文与验收目标，在受限工作区执行、验证与独立审核，并生成有证据的本地产物。

v0.1 成功标准：在临时 fixture 中，可复现 Bug 能通过完整链路生成补丁或显式授权的本地提交；任何必需验证失败、必要审核缺失、严重问题未解决或权限条件不足，都不能被标记为已完成。

业务流程是宿主控制的程序，不是模型任意生成和执行的无限循环。DSH 的工作流展示阶段不替代此状态机。[S6]

## 2. 范围

| 范围 | v0.1 必做 | 后续 |
|---|---|---|
| 原生接入 | DSH 组合包/插件、工具入口、doctor、安装卸载 | 可选原生 UI 卡片 |
| 任务 | 创建、执行、查询、取消、恢复、报告 | 工单/Webhook 入口 |
| 执行 | 一个任务一个代码写入者，Codex 为主 | 多任务受控调度 |
| 审核 | 一个独立模型路由，统一发现格式与分诊 | Claude Code、GLM 等多个审核提供方 |
| 业务流程 | 可复现 Bug 修复 | UI 修复、需求开发 |
| 交付 | patch；可配置的本地提交 | 另行授权的 PR 集成 |

首版不包含自动 push/合并/发布、生产数据库访问、独立服务平台、插件市场、可视化编排器、Dify 或机器人控制。

## 3. 架构与目录

```text
DSH launcher + 独立测试 profile
  └─ DSH DevKit bundle
       ├─ tasks：任务、状态、持久化、拥有权
       ├─ workspace：隔离任务目录、版本与产物
       ├─ context：项目规范、相关代码、任务合同
       ├─ executor：主要代码执行器适配
       ├─ verify：命令执行与证据收集
       ├─ review：独立审核、分诊、待办
       ├─ bugfix：确定性的业务流程
       ├─ policy：权限和交付约束
       └─ tools：面向 DSH 的窄接口
```

以上可以先放在一个 npm 组合包中，通过独立插件导出和配置行组合；不强制一模块一包。任务服务、状态机和存储都可以在 DSH 插件内部，不需要另建调度服务器。[S1][S3]

新项目参考结构，已有项目允许按 ADR 调整：

```text
src/
  contracts/             # 纯数据协议、校验、领域错误
  domain/                # 状态转移、gate、分诊等纯逻辑
  plugins/
    tasks.ts
    workspace.ts
    context.ts
    executor-codex.ts
    verify.ts
    review.ts
    bugfix.ts
    policy.ts
    tools.ts
  adapters/              # SQLite、Git、实际提供方映射等
  index.ts
skills/bugfix/SKILL.md
cordis.patch.yml
examples/
tests/unit/
tests/native/
tests/fixtures/
tests/live/
docs/
```

依赖方向：`tools/bugfix → 公共服务接口 → adapter`；领域协议不依赖 DSH。真实插件层负责映射 DSH Context、工具和生命周期，不能用独立 CLI 代替。辅助脚本只用于构建、测试、配置准备，不另建产品级 launcher。

## 4. 插件与生命周期合同

### 4.1 接入

插件通过受支持的 DSH bundle/profile 或 overlay 加载；编译产物、导出、patch 与 Skills 必须进入最终可安装包。不要使用 `@deepseek-ai` 命名空间发布自己的包。[S2][S3]

M0 核对工具注册、服务注入、规范输出与取消接口。工具返回可校验的 JSON，不把一段自由文本当作状态协议。[S4]

工具 schema 必须限制额外字段或明确其处理规则；跨字段、路径、权限等不变量由业务程序再次校验。

### 4.2 停止与卸载

卸载时停止接单，取消本插件拥有的运行，等待可验证的进程/任务停止，释放监听器与资源。不能删除仍可能被写入的工作区。

不得将“插件卸载”视为“代码回滚”。保留任务日志、产物和待恢复状态，清理是另一项显式操作。

### 4.3 能力发现

doctor 至少报告实际版本、注册状态、执行器与审核路由可用性、只读/写入限制、网络限制、取消能力、持久化和平台限制。

能力状态区分 `supported`、`unsupported`、`unverified`；强制程度另区分 `full`、`partial`、`none`、`unknown`。能力不足时返回类型化阻塞，不静默放宽权限。

DSH 外部子代理能力不同。不得假定主会话的模型、工具、权限、Skills、cwd 自动继承，也不能盲目使用通用 `agentOptions` 覆盖 Codex 提供方。[S5]

## 5. 配置与信任边界

本项目配置使用独立文件格式，见 `examples/devkit.config.example.json`。此文件不能直接作为 `cordis.patch.yml` 使用；实现者负责运行时校验以及与真实 DSH 配置的映射。

配置划分三类：

**宿主可信策略**：允许的仓库映射、输出目录、执行器/审核路由、命令模板、可写范围、网络授权、预算、审批入口。存储在执行器不可写的位置。

**项目上下文**：README、AGENTS.md、代码、工单、Skills。用于理解任务，不能据此提升权限、取消审核或自行批准发布。只加载必要内容，记录来源和内容 hash。[S7]

**任务输入**：用户原始描述、目标、复现材料、验收条件、任务类型。未知字段或不合法输入明确报错。模型不能传入 `approved: true` 或任意 shell 命令来获取授权。

一个配置预设可以明确授权本地受限修改与已审核验证命令，从而避免每次安全操作都询问；超出该预设才进入审批。

## 6. 数据合同

所有持久数据包含 `schemaVersion`。时间用带时区的 ISO 8601，ID 由宿主生成，凭据只保存引用。接口实现应使用明确 TypeScript 类型和运行时校验。

### 6.1 TaskInput（模型/用户可以提出的任务数据）

| 字段 | 说明 |
|---|---|
| `kind` | `bugfix` / `ui-fix` / `feature`；首版仅 bugfix 可运行 |
| `title`、`description` | 简短标题与原始任务描述 |
| `repositoryRef` | 引用宿主已授权的仓库映射，不接受任意文件系统路径 |
| `baseRef` | 可选 Git ref；宿主解析为不可变完整提交 ID |
| `reproduction` | 复现步骤、预期和实际行为、附件引用 |
| `acceptanceCriteria` | 带稳定 ID 的验收条件；需映射验证证据 |
| `verificationProfile` | 引用预配置验证计划，不传自由命令 |
| `contextRefs` | 可选已授权上下文引用 |
| `idempotencyKey` | 可选请求去重键；同 key 不同 payload 必须冲突而非覆盖 |

`executionMode`、`workspaceRoot`、权限、审批身份、模型凭据和 `readyForAcceptance` 由宿主确定，不属于可由模型自由设置的 TaskInput。

首版 `ui-fix`/`feature` 返回清晰的 `UNSUPPORTED_TASK_KIND`，不得保存为成功任务。

### 6.2 TaskRecord（宿主权威事实）

包含 taskId、原始输入 hash、解析后的仓库标识与 base commit、冻结任务合同 hash、可信策略 hash、状态与阶段、运行 ID、拥有者、预算消耗、工作区引用、当前候选快照、证据引用、审核记录、阻塞原因、创建/更新时间及 schemaVersion。

### 6.3 Snapshot

必须标识精确的待交付代码，而不只保存分支名：

`baseCommit`、可选 `candidateCommit`、`contentHash`、完整改动清单与文件模式、新增文件/二进制的 hash、依赖锁文件 hash、验证计划 hash、冻结回归测试 hash、策略 hash。

Git commit 可作为内容标识的一部分，但脏工作区不能只靠 HEAD 识别。清单需覆盖未跟踪文件；符号链接和子模块需明确处理或阻塞。

### 6.4 VerificationRun

记录 checkId、验收条件 ID、snapshotId、可信命令模板 ID、解析后的 argv、受限 cwd、环境指纹、开始/结束、exitCode、取消/超时标记、结果分类、日志 artifact 引用。

结果分类至少为 `passed`、`failed_assertion`、`failed_infrastructure`、`cancelled`、`skipped`。缺依赖、命令找不到、测试数量为零不能被算作有效复现或验证通过。

### 6.5 ReviewFinding

字段包括 findingId、fingerprint、reviewerId、实际模型/提供方标识、snapshotId、severity（P0–P3）、标题、具体位置/符号、触发条件、影响、证据引用、建议、置信信息和分诊状态。

分诊状态为 `unconfirmed`、`confirmed`、`rejected`、`resolved`、`deferred`。作者不能仅凭自我解释把问题设为 rejected/resolved。

P0：极严重的数据/安全/核心可用性问题；P1：重要功能或高风险正确性问题；P2/P3：不阻塞当前交付的中低优先级改进。等级由项目标准解释，严重程度和成立证据是两个维度。

### 6.6 Artifact 与事件

artifact 至少包含 ID、类型、相对存储引用、hash、大小、创建时间、taskId/runId/snapshotId。路径不由模型任意指定，访问必须检查范围。

事件包含递增序号、taskId、runId、stage、类型、时间和脱敏 payload。事件与状态更新保持原子一致；持久事件不是聊天文本。

## 7. 状态机与完成判定

任务状态：

| 状态 | 含义 |
|---|---|
| `queued` | 已接收，尚未执行 |
| `running` | 正在某一阶段 |
| `blocked` | 缺配置、环境、权限、可验证复现等，不能继续 |
| `awaiting_human` | 等待业务决定、严重发现处理或最终验收，必须带具体 reason |
| `cancelling` | 已请求取消，尚未证明执行资源停止 |
| `cancelled` | 本次执行已停止且未作为完成交付 |
| `interrupted` | 运行被中断，实际副作用需要核对 |
| `failed` | 不可恢复或当前运行失败 |
| `completed` | 人类明确接受本地产物；不代表合并/上线 |

运行阶段：`preflight → context → reproduce → implement → snapshot → verify → review → triage → package`。

失败返修可从 verify/triage 回到 implement，但必须增加返修计数、产生新快照并重跑必要验证与审核。所有状态转移由程序判断并记录，模型不能直接写数据库修改状态。

最终 `readyForAcceptance = true` 的条件必须全部成立：

- 已有有效复现，且验收条件全部有对应通过证据。
- 必需验证全部在当前精确快照、冻结测试和有效计划上通过。
- 必需审核器全部成功返回合法结果，并覆盖当前快照。
- 确认 P0/P1 为零；未确认但有具体风险依据的高优先级问题已经补证或交人处理，不能被静默跳过。
- 没有越权修改、测试/策略篡改、未关闭的写入执行器或无法证明的副作用。
- 所有预算、权限和合同约束满足。

此时进入 `awaiting_human`，reason=`final_acceptance`，不是自动 completed。人类确认后可置 completed，仍不执行 push/merge/deploy。

`awaiting_human` 中其它 reason 的任务不得显示成“已通过待验收”。展示必须带 `readyForAcceptance` 及阻塞原因。

## 8. Bug 修复流程

### 8.1 Preflight

校验仓库授权、版本、目录、依赖、验证计划、执行器、必要审核器、沙箱与预算。缺必需审核器时尽早阻塞 live 任务，避免先花费整轮开发成本。

读取主工作区状态并保留记录，不 stash、不 reset、不清理用户修改。默认从指定已提交 base 创建任务工作区；未提交修改不自动复制。确需包含时先取得明确授权并生成独立基线快照。

### 8.2 Context

加载相关项目规范与最小相关代码，形成任务合同。普通局部实现决策由 Agent 自查；涉及未知业务规则、权限或接口变化时进入 awaiting_human，不自行补全。

合同冻结后生成 hash。scope/验收变化使原来的审批和相关证据失效。

### 8.3 Reproduce

先重现旧代码的目标失败。可由 Agent 提议新回归测试，但宿主验证其确实在未修复生产代码上以预期断言失败。

推荐做法：基准源码 + 新增回归测试 overlay，单独记录测试内容 hash；复现阶段不得悄悄修改生产实现。测试从缺文件/网络错误/安装失败退出不算复现。

有效回归测试冻结后，修复阶段不得擅自改变其断言、跳过标记或阈值。需要改变必须请求受信任审批并重新建立复现基线。

无法复现时返回 blocked，reason=`not_reproduced` 或 `insufficient_evidence`，附定位信息；不能声称已修复。

### 8.4 Implement

只有主要执行器获得受限代码写权限。每次调用都绑定 taskId/runId、任务合同、允许范围、截止时间与取消信号。

执行器可以修改授权代码，不能编辑宿主策略、审核记录、凭据、插件执行基础设施或验收证据。不得自动执行 git push/merge/rebase、危险清理或更改远端配置。

依赖安装和脚本执行需要预先授权的计划。`npm test` 等名字本身不是安全证明，脚本及其依赖执行同样要在受限环境运行。

### 8.5 Snapshot 与 Verify

执行器停止并确认无写入者后，宿主捕获候选快照。基于冻结回归测试和完整验证计划运行检查。

检测验证前后的输入代码变化。测试生成的已声明构建产物可落到指定输出区；任何源代码或受保护测试变化使结果失效。

lint、类型检查、构建、回归测试是否必需，取决于已冻结的项目验证计划；没有某项工具时不能伪造通过，也不强制无关工具。

### 8.6 Review 与 Triage

独立审核在新的、未继承写作者推理上下文的会话/调用中进行。提供原需求、验收、基准与候选 diff、必要上下文、验证证据，不只提供作者结论。

默认一个必要审核器，优先 DeepSeek。实现可配置审核数组和 required 标志；live 验证要求至少一个与写作者不同模型系列的必要审核器，不能仅换名字或会话冒充。

无工具的模型审阅由宿主提供脱敏只读上下文；带工具审核器必须证明只读边界，且不得访问执行器之外的凭据或真实用户环境。

审核输出用明确 schema 校验；不支持原生结构化输出时可以宿主严格解析一次并有限请求格式修正，仍失败则 review_error。不得把解析异常转成空 findings 后通过。

分诊规则：

| 结果 | 动作 |
|---|---|
| 证据确认的 P0/P1 | 阻塞，加入修复；修复后新快照重新验证/审核 |
| 疑似 P0/P1 且证据不足 | 一次有预算的补证；仍有争议则 awaiting_human |
| P2/P3 且不违反本次验收 | 去重后 deferred，进入本地待办池 |
| 必需验证失败/验收不满足 | 始终阻塞，不受模型 severity 影响 |
| 必需审核超时/不可用/非法输出 | 阻塞，不能按多数票忽略 |
| 可选审核失败 | 记录缺口；不得声称所有审核器通过 |

自动确认应有重现实验、测试或可核对的明确证据；“另一个模型也同意”不能单独充当事实证明。证据无法机械确认时允许人工决定。

发现去重基于规则/符号/位置与问题语义指纹，保留每次原始出现与快照；不能只按标题合并不同问题。旧发现标 resolved 必须有新版本证据或受信任人工决定。

### 8.7 有限返修与交付

默认最多 **2 次自动返修**，不含首次实现，即最多 3 次代码实现尝试。测试失败返修和审核返修共用这个上限；运行恢复不能重置计数。

预算还包含模型调用次数、运行时限、阶段时限和日志/上下文大小。token/费用只有提供方可准确提供时才记录，不能估计为 0；要求硬费用上限但无可执行计量时明确能力不足。

到达上限：停止并输出未解决问题及产物，awaiting_human 或 failed，不能无限循环。

默认输出 patch。配置明确授权且 Git 身份/签名/钩子要求满足时，可由宿主在**任务分支**生成本地提交，随后仍需对该精确版本验证和审核。不得伪造作者、绕过组织签名/钩子政策或自动 push。提交能力不足时保留 patch 并说明，不能谎称已有提交。

若先做内容快照验证再生成提交，必须证明最终提交内容与快照一致，否则重跑验证/审核。

## 9. 安全与工作区

### 9.1 工作区不是安全边界

Git worktree 用于避免混杂工作目录，并不构成进程、网络或所有 Git 元数据的隔离。[S12]

可采用 worktree 加可验证沙箱；若不能安全限制共享 Git 元数据，则改用独立沙箱副本/独立仓库工作区。工作区提供方可替换，不能把不具备隔离的路径拼接包装成沙箱。

目标任务目录必须在宿主批准的根下，不在插件源码目录或用户当前工作目录中。清理只能删除宿主证明拥有且已停止运行的目录，默认保留以便人工检查。

### 9.2 强制权限

策略至少区分文件读取、文件写入、命令执行、网络出站、仓库管理和交付操作。

DSH 的文件沙箱模式不自动保证网络限制，且部分平台可能只提供 partial 强制执行；适配器必须准确上报。[S8]

默认禁止任意网络。模型服务自身经授权端点通信，与执行代码访问网络是两个权限面；不能因“模型要联网”就给 shell 全网络权限。

在无法满足要求的平台上，doctor 返回 unsupported/partial 并阻塞 live 写入，或要求用户明确启用有说明的降级策略；默认不得静默降级。首版不必为每个平台新写 OS 沙箱，但要如实暴露实际支持矩阵。

### 9.3 路径、命令与凭据

路径校验需处理 `..`、绝对路径、符号链接、大小写/分隔符、Windows 盘符与 UNC 等边界；对不存在目标检查真实父目录。仅 `startsWith(root)` 不足以证明安全。

外部命令使用可验证的可执行文件与参数列表，禁止把任务文本拼接成 shell 命令；Windows 包管理器启动差异要有专门处理和测试。

env 采用最小允许集合。模型端点密钥只给必要适配器，不下发到测试/执行 shell、不写任务上下文。日志、diff 和代码片段上传前需按授权范围过滤，并限制大小。现有密钥误入代码时也不能照单外发。

仓库内容、工单、网页、模型结果中的“忽略规则/打印密钥/跳过审核”不能改变宿主权限。审批动作不能暴露给普通执行器自调用。

### 9.4 审批

审批与 taskId、动作、参数 hash、快照/合同 hash、范围、有效期和受信任操作者绑定。由 DSH 受信任交互或明确宿主操作提交，不接受模型自行声明的 actor/approved 字段。

合同、范围或候选版本变化后，受影响审批重新获取。人工批准一次局部修复不等于批准 push、部署或未来任意任务。

## 10. 持久化、取消和恢复

### 10.1 存储

首版单机，本地 SQLite 作为默认实现；驱动在 M0 按实际 Node/系统兼容性选择并锁定。已有等价事务存储可复用，但必须在 ADR 证明满足约束；不引入外部数据库服务。

数据库和证据目录位于执行器不可写的宿主数据根。通过 Store 接口解耦，记录 schemaVersion；迁移失败不得静默重建丢失任务。

状态变更和事件写入在同一事务；避免“状态成功但证据未写入”。不改写 DSH 内部 Session schema 来充当自定义任务数据库。

### 10.2 防重与单写入

使用持久 request 去重键、状态版本检查、任务拥有权、宿主运行锁。相同任务只能存在一个被授权写入者；默认同一仓库任务串行运行。

dispatch 前持久记录 operationId、attempt、预计动作与已有产物；完成后记录结果。无法保证外部副作用 exactly-once，因此恢复必须核对实际结果而非直接重发。

不要仅凭 heartbeat 超时就启动第二个执行器。必须确认旧执行者停止或失去写权限，无法确认则 interrupted/blocked。PID 复用、多个 DSH 进程和同一数据库竞争要纳入测试。

### 10.3 取消

取消沿任务 → 子代理 → 命令进程传播，并等待确认停止。只有“已发取消信号”不能置 cancelled。

无法证明停止时保持 cancelling/interrupted、继续保留锁或隔离访问，不允许删除工作区或启动新写入者。生命周期处理要幂等。

### 10.4 恢复

重启发现未完成执行时标记 interrupted，读取已保存证据、Git 状态、候选快照和操作日志。

显式恢复前重做必要 preflight：配置与合同是否改变、工作区是否被人工修改、旧进程是否已停止、审核/测试是否仍针对当前版本。

保留返修/预算计数。只能重用与快照和环境完全匹配的可重用证据；存在不确定副作用时先人工处理，不能无限重试提交或模型调用。

## 11. DSH 工具入口（拟实现）

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `devkit_doctor` | 检查版本、配置与可用能力 | 不泄露凭据，不擅自执行付费模型探测 |
| `dev_task_create` | 创建、校验合同 | 无代码执行权限，支持幂等 |
| `dev_task_run` | 启动已授权任务 | 首版受限运行，不接受自由权限覆盖 |
| `dev_task_status` | 获取状态、阶段与阻塞 | 只读，返回结构化结果 |
| `dev_task_cancel` | 取消自己的任务 | 正确处理取消过程与最终停止 |
| `dev_task_resume` | 显式恢复中断任务 | 必须重核验，不重置计数 |
| `dev_task_report` | 导出结果与待办 | 只读取宿主拥有的产物 |

工具名为本项目设计。最终审批入口应是受信任人类控制面，不是对代码执行器暴露 `approve_anything` 工具。

长任务可采用真实 DSH 所支持的 job 机制或显式运行句柄，并返回 taskId；必须验证父会话结束、插件卸载和重启时的所有权语义。不能创建失去管理的 detached promise。简单的受控同步入口也可作为首版实现，需满足取消和查询要求。[S4]

## 12. 测试 fixture 与模式

默认 fixture 是临时创建的小型 TypeScript 分页工具仓库，不引用用户真实项目。

示例规则：`normalizePage(input)` 对 undefined、0、负数、非整数、NaN、Infinity 返回 1，对正整数原样返回。故障版本仅使用 `input ?? 1`，导致非法数值未归一化。测试应由 fixture 明确规定，不由执行器随意选择预期。

三种验证证据分开：

- `unit`：纯逻辑与适配器测试，可使用 mock。
- `native-fixture`：真实锁定 DSH runtime + 插件装配/工具分派 + 明确标识的测试执行器；不用模型费用。
- `live`：真实 Codex 和独立审核模型，在显式开关及已授权配置下运行同一临时 fixture。

测试替身不得在 live 模式被静默启用。缺凭据时 live skipped/blocked 不是 passed。首版交付报告必须按这三个层次分列。

验收详情以 `ACCEPTANCE.md` 为准。

## 15. 可观测性、打包和最终交付

日志记录任务/运行/阶段/调用关系；在提供方暴露实际用量时记录 tokens/cost，否则显示 unavailable，不推算成免费。设置日志、上下文和产物大小上限。

打包测试应从安装产物而非源码目录启动；验证 patch、导出、Skills 和运行依赖完整。不要只证明开发模式可用。[S3]

`docs/IMPLEMENTATION_STATUS.md`、`docs/DSH_COMPATIBILITY.md`、`docs/SECURITY.md`、`docs/TEST_REPORT.md`、`docs/QUICKSTART.md` 为交付物。记录真实命令、实际平台与未验证平台、各类测试结果和已知限制。

完成度必须来自证据，不是 README 的功能列表。v0.1 中未实现的未来能力要明确标注 deferred；无真实模型接入证据时，不能声称已验证完整生产可用性。
