# 给 Codex 的首轮执行提示词

你现在是这个项目的实施负责人。请在当前工作区实现 **DSH DevKit**：基于 DeepSeek Harness 的可组合研发辅助插件。我要的是可运行代码、测试和安装说明，不是再写一份方案。

## 一、先读这些文件

读取当前工作区和上层适用的 AGENTS.md，然后按顺序读取：

1. `dsh-devkit-handoff/README.md`
2. `dsh-devkit-handoff/PLAN.md`
3. `dsh-devkit-handoff/SPEC.md`
4. `dsh-devkit-handoff/ACCEPTANCE.md`
5. `dsh-devkit-handoff/SOURCES.md`
6. `dsh-devkit-handoff/examples/` 下的配置与任务样例

包的位置不在此路径时，先定位这组文件，不要编造不存在的内容。`templates/AGENTS.append.md` 只可按需合并，不得覆盖既有 AGENTS.md。

## 二、此次交付范围

完成 PLAN 中 **M0–M3，即 v0.1 可复现 Bug 修复闭环**。后续 UI 修复、需求开发按 SPEC 保持扩展接口，但此次不要自动开始 M4/M5。

闭环必须是：

任务接收 → 上下文与验收合同 → 可核验复现 → 隔离工作区中的 Codex 修改 → 精确快照 → 真实验证 → 独立模型审核 → 问题分诊 → 最多两轮自动返修 → 本地产物与待人工验收报告。

确认的 P0/P1 阻塞交付；其它问题进入待办，但不能豁免验收或测试失败。不能只因为模型说“完成”就置成功。

## 三、代码放在哪里

先检查当前目录。空项目可直接初始化；已有 DSH 插件项目优先扩展其合理结构。若当前目录只是普通业务仓库，默认将新插件项目隔离在 `tools/dsh-devkit/`，不要重写业务源码，也不要把业务仓库改造成 DSH fork。

业务测试必须使用自动创建的临时 fixture 仓库，不要把插件源码仓库当作修 Bug 的目标仓库。

默认 TypeScript strict、ESM，具体 Node/包管理器/依赖与锁定 DSH 版本兼容；已有合理工具链优先沿用。

## 四、实施要求

先执行 M0 的最小代码考古和 API 核验，输出环境、兼容性和布局结论，然后继续实现。不要把“先写计划”当作本次终点，也不要为非阻塞的小选择反复询问。

所有 DSH 接入必须由实际安装版本的类型/源码或官方文档证明。不要杜撰包名、配置、ctx 字段或 SDK 方法，也不要用 any、假 Context、空适配器绕过兼容问题。新依赖锁版本，不直接写 latest。

通过真实 DSH profile/bundle 或受支持的 overlay 装配插件。应用入口仍由 DSH launcher 提供，不另起一个 Node 主程序冒充 DSH 产品接入。

优先复用 DSH 的 Codex 子代理提供方。首版独立审核优先接入已配置的 DeepSeek 路由；没有配置时实现完整适配器与阻塞路径，不能用 Codex 自审冒充跨模型审核。Claude Code、GLM 不必同时接完。

权限、任务状态、验收、重试、快照和报告由程序控制。普通模型输出不能改变审批、执行权限、验证计划或成功判定。

不要覆盖未提交修改、运行危险全局命令、修改全局 Codex/DSH 配置、自动 push、自动合并、部署或发布 npm 包。

## 五、多代理和模型分工

主代理负责架构、关键实现与最终整合，使用当前环境已授权且可用的高推理 Codex 配置。

支持子代理时，先并行安排两个只读任务：A 核对 DSH 接入与版本；B 审查 SPEC 的状态机、验证与安全测试要求。主代理等待并整合结果，不让子代理同时修改同一组文件。

代码实现保持单写入者。测试/独立审计可使用不同只读子代理。简单代码扫描可使用当前环境中已确认可用的轻量模型；高风险评审用支持的高推理档。不要编造模型 ID，不要宣称提示词能切换不可用模型或访问外部账号。

环境不支持子代理或独立模型选择时，用当前会话顺序完成，并如实记录；不能因为缺少多代理功能就不实施。

这里的“Codex 开发时使用子代理”与“将来插件运行时的多模型审核”是两套职责，不能混淆验证结果。

## 六、测试与真实接入

优先建立可独立运行的领域测试，再实现真实 DSH 接入测试。离线 fixture 允许 fake 执行器/审核结果，但必须显式标记为测试替身。

必须提供真实 DSH 挂载和工具分派测试，不能只有 mock Context 测试。

真实模型联调用显式开关开启，只在已有授权的测试配置和临时 fixture 中执行；不要读取或打印密钥，不得擅自把真实业务源码上传给新提供方。缺少凭据/网络/平台能力时，继续完成不受阻部分，列出阻塞和准确补齐步骤。不能把 skipped 当 passed。

逐项执行 ACCEPTANCE.md。至少证明：成功闭环、P1 返修、超限停止、无复现不宣称修复、测试失败不交付、旧快照证据失效、审核缺失/异常不通过、只读边界、取消、重启防重、安装与卸载。

## 七、过程与最终交付

开始时简要说明检测到的项目类型、实施位置和第一个里程碑，然后写代码。每完成一阶段，更新 `docs/IMPLEMENTATION_STATUS.md`，记录实际测试命令和结果。

不得用 TODO、空实现或永远返回成功的 fake 来满足正式接口。遇到真实能力不足，输出类型化阻塞，不掩盖。

最终报告必须给出：

- 已实现模块、源码位置和剩余项。
- 锁定的 DSH/执行器版本与兼容性证据。
- 实际运行过的安装、启动和测试命令。
- 单元测试、原生 DSH 接入、真实模型联调分别的 passed/failed/skipped。
- 临时示例任务的输入、补丁/本地提交、验证、审核和报告路径。
- 安全限制、已知问题，以及剩余配置步骤。

默认只保留本地修改/交付产物，不 push。未完成时明确写未完成；上下文不足时保存精确进度与下一步，不要把整个项目标为完成。

现在开始 M0，并在核验完必要接口后继续实施 M1–M3。
