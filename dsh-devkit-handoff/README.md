# DSH DevKit · Codex 开发交接包

**目标：基于 DeepSeek Harness，开发可组合的研发辅助插件，而不是另外造一个代码 Agent。**

版本：Spec 1.0 · 2026-09-20  
性质：实施计划、产品/技术规范与执行提示词；**不是已经实现或测试过的插件程序**。  
默认首轮交付：v0.1，可复现 Bug 的修复、验证、独立审核与本地产物交付闭环。

## 怎么交给 Codex

在准备用于开发插件的项目目录中放入整个 `dsh-devkit-handoff/` 文件夹。没有现成插件项目时，可新建一个空目录 `dsh-devkit`，在 Codex 中打开它，再放入本文件夹。

把 `CODEX_PROMPT.md` 的正文作为第一条任务发给 Codex。也可以只发：

> 阅读当前目录下 `dsh-devkit-handoff/CODEX_PROMPT.md` 以及其中指定的文档，按照里面的要求开始实现。此次先完成 M0–M3 的 v0.1，不要停在方案说明，不要自动进入 M4/M5，也不要修改无关业务代码。

已存在的 `AGENTS.md` 必须保留。本包的 `templates/AGENTS.append.md` 是待合并规则，不是让你直接覆盖根目录文件。

## 文件导航

| 文件 | 用途 |
|---|---|
| `PLAN.md` | 分阶段实施、依赖、交付物与停止条件 |
| `SPEC.md` | 插件边界、任务协议、流程、审核、权限、持久化等规范 |
| `ACCEPTANCE.md` | 逐项验收用例，防止“只有 mock”或“只有接口” |
| `CODEX_PROMPT.md` | 第一轮执行提示词：完成 M0–M3 |
| `CODEX_REVIEW_PROMPT.md` | 在新会话进行独立实现审计的提示词 |
| `CODEX_CONTINUE.md` | 中断续做、第二期 UI 修复、第三期需求开发提示词 |
| `SOURCES.md` | 已核对的官方文档、证据边界与版本核验要求 |
| `examples/devkit.config.example.json` | 本项目拟实现的配置格式，不是可直接交给 DSH 的配置 |
| `examples/task.bugfix.json` | 第一版示例任务合同，指向测试 fixture 而非真实业务仓库 |
| `templates/AGENTS.append.md` | 建议合并到插件仓库的 Codex 工作规范 |

## 三期路线

**v0.1：Bug 修复。** 真正挂载到 DSH，接收任务，准备隔离工作区，调用 Codex，运行验证，独立模型审核，有限返修，输出待人工验收产物。

**v0.2：UI 修复。** 复用公共能力，增加页面启动、参照材料、截图、视觉及交互验证。

**v0.3：需求开发。** 复用公共能力，增加需求澄清、验收条件冻结、方案审批和功能开发。

首版不建设插件市场、独立 Web 工作台、Dify 流程、多租户服务或自动上线能力。

## 四条底线

1. DSH 原生插件是真正入口；独立命令行脚本或 HTTP 服务不能冒充已完成 DSH 接入。
2. Codex 是主要代码执行器；独立审核优先使用已配置的 DeepSeek 路由，后续可增加 Claude Code、GLM。没有可用审核配置时明确阻塞，不能假装完成多模型审核。
3. 测试、审核、审批绑定精确代码快照；修改后旧证据失效。确认的 P0/P1 阻塞交付，其他问题收集，但不能豁免本次验收失败。
4. 默认不 push、不合并、不部署、不改全局工具配置。产物停在本地待人工验收。

## 交付结果要怎样读

实现者必须分别报告：

- **代码完成度**：哪些模块真实实现，哪些仍有缺口。
- **离线验证**：无需付费模型、在临时 fixture 中跑出的测试。
- **DSH 原生接入验证**：是否真实启动锁定版本 DSH，并通过真实工具注册/分派路径执行。
- **真实模型验证**：是否实际调用 Codex 和独立审核模型；未运行必须写“未验证”及原因。

“离线测试通过”不等于“真实模型效果验证通过”。本交接包本身也不声称已经完成以上任何程序测试。
